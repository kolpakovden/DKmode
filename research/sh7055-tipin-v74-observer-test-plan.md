# v74 — модель OEM Tip-in, план логирования и критерии решения «калибровка или DKmode»

**Дата:** 2026-10-26. **Статус:** офлайн-модель и план испытаний; ROM не изменялся, BIN не создавался. Работа не связана с Delta MAP.

Исходные результаты: [v69](sh7055-tipin-v69-static-trace.md) – [v73](sh7055-tipin-v73-output-state-machine.md). Всё, что получено на proxy-ROM, остаётся `PROXY-CONFIRMED`.

## 1. Офлайн-модель штатного Tip-in

Файл `tools/analysis/sh7055_tipin_model_v74.py` — read-only, без зависимостей.

- Принимает только ROM с известным SHA-256: v39, v25 или семь proxy v63–v70. Статус выводится в отчёте.
- Перед расчётом сверяет литеральный пул `0x24A04` (11 указателей, включая `0x54910/0x5455C/0x54924`, `0x58DA4/58DA8/58DAC`, `0x58852/53/54`, `0x209C`, `0x1763A`). Если код Tip-in в ROM другой, модель отказывается работать.
- Все калибровки читаются **из одного указанного файла**. Модель не смешивает v25, v39 и proxy и не хранит значений «по умолчанию».
- Повторяет логику `0x24A04` в порядке кода:
  1. `B821++` (до 255);
  2. при Δ < 0 — `B818 = B814 = 0`, иначе сбросы по `B821 ≥ ROM8[0x58853/54]`;
  3. отказ, если `Δ < ROM_f[0x58DA4]`, `B818 ≥ ROM8[0x58852]`, стоит одно из внешних условий или `B814 ≥ ROM_f[0x58DAC]`;
  4. `B80C = T(Δ)·K_boost(AF08−AF94)·K_ect(B090)` по интерполятору `0x209C`: ограничение на краях оси, линейная интерполяция, `raw·mult + off`, тип данных по байту +2;
  5. срабатывание, если `B80C ≥ ROM_f[0x58DA8]`; затем `B818++`, `B814 += Δ`, `B821 = 0`.
- Δ считается как `B024[n] − B024[n−2]` на каждом прогоне задачи №9. Период задаётся параметром `--period-ms` (по умолчанию 8.0 — **оценка при Pφ = 20 МГц, не измерение**). Можно добавить джиттер исполнения (`--jitter-ms`).
- Не моделируются (задаются как предположения): внешние условия `B018.1` и `B469.7`, маска цилиндров `B434`, подстановка 6.0 при неисправности TPS, потери активаций, слияние с основным импульсом (v73 §2.2). Перевод % → `B024`: `× 0.84` (RomRaider E38, `REFERENCE`).

### 1.1. Пример (proxy v63; калибровки v63, **не v39**)

`--calib`: `min_delta` = 0.5, `min_amount_us` = 385, `max_cum_delta` = 23, `max_events` = 7, сбросы через 22 прогона. `T(Δ)`: 384…5724 мкс на оси 0…31.3; `K_boost`: 0.5 при ошибке наддува ≤ 64 мм рт. ст. и 1.0 при ≥ 128; `K_ect`: 3.66 при −40 °C … 1.0 при ≥ 80 °C.

| Сценарий (ошибка наддува 200 мм рт. ст., ECT 85 °C) | Срабатываний | Σ добавки, мкс | Остановлено |
|---|---:|---:|---|
| 5 → 15 % за 100 мс | 7 | 3369 | лимит `B818` (7) |
| 5 → 35 % за 120 мс | 7 | 5009 | лимит `B818` |
| 5 → 80 % за 60 мс | 3 | 6616 | лимит накопленного Δ `B814` (23) |
| 10 → 12 % за 200 мс | 0 | 0 | Δ < 0.5 |

Вывод для плана испытаний: при медленном и умеренном нажатии добавку на proxy ограничивает **лимит числа событий**, при резком — **накопленный Δ**, а не порог величины. Эти пары и нужно проверять на автомобиле. Для v39 таблицу надо пересчитать по его собственному BIN.

## 2. Требования к логированию

### 2.1. Сначала — идентификация ROM на автомобиле

Перед любым сравнением нужно считать ROM, установленный в ECU, и вычислить его SHA-256. Модель и выводы применимы только к этому файлу. Если хеш не совпадает с v39 или proxy, сначала повторить сверку литерального пула и аудит v70.

### 2.3. Реальная частота опроса — ограничение интерфейса

> **Уточнение v75:** реальные логи автомобиля (`forester_A2WC012E`, v68, 2026-09-01/02) показывают интервал **48–50 мс** при ≈ 13 адресах SSM, то есть RomRaider работает в режиме непрерывного ответа ECU (fast poll), а не «запрос-ответ» на каждый отсчёт. Оценки ниже занижают частоту в 2–4 раза. Новая оценка и метод измерения — в [v75](sh7055-tipin-v75-measurement-readiness.md) §3. Вывод «8 мс по SSM недоступно» остаётся в силе.

SSM по K-line, 4800 бод (протокол в логгере: `SSM baud="4800"`), 10 бит на байт, ≈ 2.08 мс на байт. Чтение A8 из N адресов (каждый байт float — отдельный адрес):

```text
запрос = 7 + 3N байт, ответ = 6 + N байт  →  время на шине ≈ (13 + 4N) · 2.083 мс + задержки ECU
```

| Набор | N адресов | Время на шине | Частота (верхняя оценка) |
|---|---:|---:|---:|
| Полный (8 float + B818, B821, 94E4, 94F0, RPM, ECT, A/F) | 41 | ≈ 369 мс | ≈ 2.7 Гц |
| Минимальный (B024, B028, 94F0, B818) | 11 | ≈ 119 мс | ≈ 8 Гц |
| Только счётчики (B818, 94E4, 94F0, B80C) | 8 | ≈ 94 мс | ≈ 10 Гц |

Задержки ответа ECU в расчёт не входят — реальная частота ниже. **Через SSM по K-line наблюдать события с шагом 8 мс невозможно.** Если ECU поддерживает SSM поверх CAN (ISO 15765), частота выше, но это тоже запрос-ответ, и поддержку на этом JDM-блоке нужно проверить подключением. Обещать 8 мс по диагностическому интерфейсу нельзя.

Что SSM даёт надёжно, несмотря на низкую частоту:

- **Защёлкнутые значения:** `B80C` (последняя добавка), `B818`, `B814`, `B821` — по ним видно, было ли событие и сколько их в серии.
- **Проверка тактирования:** `94F0` увеличивается на 1 каждые 2 тика CMT1. За минуту лога (с поправкой на переполнение 16 бит) отношение Δ`94F0` к времени ПК даёт фактический период тика с точностью до долей процента. Ожидание при Pφ = 20 МГц — **500 отсчётов/с** (тик 1 мс). Это первая прямая проверка оценки «8 мс».
- **Потери активаций:** `94E4`. Рост на холостом ходу и под нагрузкой — признак джиттера, который модель должна учитывать.

### 2.4. Внешняя быстрая регистрация (обязательна для временных метрик)

| Канал | Где снимать | Частота дискретизации | Зачем |
|---|---|---|---|
| Управляющий сигнал форсунки 1 (и 2–4, если есть каналы) | нижний вывод форсунки или токовые клещи | ≥ 50 кГц | прямое наблюдение доп. импульса Tip-in, его длительности и времени |
| Напряжение TPS (основной канал) | сигнальный провод датчика заслонки | ≥ 1 кГц | точное время и скорость открытия; общая шкала с B024 |
| Широкополосный λ | аналоговый выход контроллера | ≥ 100 Гц | бедный провал; учитывать собственную задержку датчика и газового тракта |
| Обороты | импульсы форсунки или датчик коленвала | ≥ 10 кГц | условия испытания |
| Метка синхронизации | общий для DAQ и ПК (например, ступенька TPS) | — | сведение с SSM-логом по B024 |

Логгер должен писать метку времени ПК на каждый ответ SSM (а не время запроса) и параметры одного ответа хранить вместе. Внешний DAQ и SSM сводятся по взаимной корреляции TPS: аналог против B024.

## 3. Методика контролируемого сравнения

### 3.1. Что сравнивается

1. **Фаза O (только наблюдение, текущий ROM):** проверить модель против автомобиля — совпадают ли число и величина событий (`B818`, `B80C`, доп. импульсы на форсунке) с расчётом модели по тому же TPS.
2. **Фаза A/B (только после отдельного решения владельца о BIN):** две калибровки одного и того же штатного кода, например A — текущая, B — изменённые пороги или лимиты серии. Сравнение «Subaru против CarBerry» на одном двигателе невозможно, пока алгоритм CarBerry не реализован. Сравнивать с CarBerry можно только **модельно**, и только после подтверждения единиц HC16 (§4).
3. **Опорный вариант:** Tip-in фактически выключен (например, `min_amount` выше максимума таблицы) — даёт вклад Tip-in в переходный режим. Тоже только после решения о BIN.

### 3.2. Контролируемые условия (каждая ячейка)

- ECT ≥ 80 °C (`K_ect` = 1.0 по v63) и стабильная IAT ± 5 °C; учесть `K_ect` при холодном двигателе отдельно.
- Передача фиксирована (например, 3-я), обороты в начале — точки 2000 / 3000 / 4000 ± 100 об/мин.
- Начальная нагрузка: MAP в окне ± 20 мм рт. ст. и начальное открытие заслонки ± 1 %.
- Ошибка наддува (`AF08 − AF94`) записывается: она меняет `K_boost` (0.5…1.0 по v63).
- Скорость открытия: классы по фактическим ΔTPS / Δt из внешнего канала — медленно (≈ 50 %/с), средне (≈ 200 %/с), резко (≥ 800 %/с). Желателен механический упор педали для повторяемости.
- Перед повтором — пауза ≥ 22 прогонов задачи №9 (по v63 сбросы `B818/B814` через 22 прогона; около 0.2 с при 8 мс), а лучше 2–3 с.
- Повторов на ячейку ≥ 10, порядок вариантов перемешивать. Закрытый или открытый контур и A/F learning фиксировать в протоколе.

### 3.3. Измеряемые показатели

| Показатель | Определение | Источник |
|---|---|---|
| Пиковое отклонение λ | `max(λ − λ_цели)` в окне 0…1 с от начала открытия | внешний WBO2 + цель (A/F target) |
| Бедная площадь | `∫ max(0, λ − λ_цели) dt` | внешний WBO2 |
| Задержка обогащения | от начала открытия (TPS аналог) до первого доп. импульса на форсунке | DAQ |
| Задержка реакции λ | от начала открытия до минимума или пика λ (с поправкой на задержку датчика) | DAQ |
| Величина добавки | сумма ширин доп. импульсов за событие против `B80C` | DAQ + SSM |
| Повторные срабатывания | число доп. импульсов на одно нажатие; вероятность ≥ 2 | DAQ, `B818` |
| Причина остановки | `B818` = лимит / `B814` ≥ лимита / Δ < порога | SSM + модель |
| Потери активаций | приращение `94E4` за тест | SSM |
| Фактический тик | Δ`94F0` / Δt | SSM |

## 4. Пороги CarBerry и Subaru — что нужно для сопоставления

**Сейчас пороги несопоставимы.** Ниже — подтверждённое и недостающее.

| Звено | Subaru | CarBerry |
|---|---|---|
| Сравнение порога | с `B80C` в мкс (v72; `PROXY-CONFIRMED`) | `0xA8B8: CPE 0x293FA,EK` — с величиной после компенсаций, в сырых единицах таблицы (`REFERENCE`, заметки forester) |
| Физическая единица | мкс: множитель 4.0 дескриптора + латентность `B8D8` в мкс + такт DCNT 4 мкс (тот сходится только при Pφ = 20 МГц) | **не доказана**: `x·0.004 мс` — только из XML |
| Δ TPS | float, окно 2 прогона (≈ 16 мс при оценке 8 мс) | `128 + q8[n] − q8[n−2]`, окно ≈ 30 мс при условном кварце |

**Доказательства, необходимые для сравнения:**

- CarBerry BIN (`b06e1282…`) и трассировка от величины, сравниваемой с `0x293FA`, до регистра таймера выхода HC16 (TPU/GPT), включая предделитель и частоту системы.
- Реальный кварц CarBerry, чтобы подтвердить период обновления Δ.
- Связь QADC-канала `0x30` с датчиком заслонки.

До этого **никаких выводов о превосходстве** одного алгоритма. Таблица v73 §5 («62.5 / 6.25 / 96 сырых единиц») — сравнение в сырых единицах при допущении 4 мкс, а не доказанное физическое.

|---|---|---|---|---|

| Адаптивная база TPS | `0x03C8` | обучаемый ноль `80E8` + `80A0` | нет (аналог есть) | — |
| Порог Δ и порог величины | есть | есть | нет | калибровка `0x58DA4/0x58DA8` |

| Компенсации наддува и ECT | есть (в формуле фактора) | `K_boost` (`0x5455C`), `K_ect` (`0x54924`) | нет | калибровка |
| **Компенсация по оборотам** | `factor = rpm·boost·ect` (заметки forester, `REFERENCE`) | `B80C = T·K_boost·K_ect` — оборотов **нет** в коде `0x24A04` | **да, вероятно** | см. ниже |
| Длина окна Δ ≈ 30 мс | условно | ≈ 16 мс (оценка) | отличие, не отсутствие | калибровочное приближение: масштаб оси `T(Δ)`; для линейного нажатия Δ₁₆ ≈ Δ₃₀·16/30 |
| Подача по цилиндрам | не трассирована | все 4 одновременно, с маской `B434` | неизвестно | сначала трассировка HC16 |

**Компенсация по оборотам — единственный кандидат на функцию DKmode.** Подтверждение со стороны CarBerry — только `REFERENCE`.

- **Сначала — калибровочная проверка:** на автомобиле в фазе O определить, зависит ли нужная добавка от оборотов при равных Δ, `K_boost` и `K_ect`. Если нет — функция не нужна.
- **Если зависит**, минимальная независимая реализация (спецификация, не BIN): отдельный 1D-множитель `K_rpm(rpm)` (оси и значения калибруются), применяемый к `B80C` **до** сравнения с `0x58DA8`. По умолчанию все `K_rpm = 1.0` — тогда поведение побитно совпадает со штатным. Вход — RAM оборотов (адрес подтвердить), выход — та же переменная `B80C`. Никаких изменений таймеров и выхода форсунок. Точка встраивания, свободная ROM/RAM и ABI выбираются только после отдельного решения владельца (roadmap).

## 6. Критерии решения: калибровка или DKmode

**Решение «достаточно штатных калибровок»**, если выполнены все условия:

1. Модель на ROM автомобиля совпадает с наблюдением: число событий на нажатие — в ≥ 90 % повторов, `B80C` — в пределах ± 10 %.
2. Бедный провал устраняется изменением только `0x58DA4`, `0x58DA8`, `0x58852..54`, `0x58DAC`, `T(Δ)`, `K_boost`, `K_ect` в пределах их осей, без насыщения таблиц на краях.
3. После изменения пиковое отклонение λ в каждой ячейке ≤ порога владельца (предложение: Δλ ≤ +0.05 относительно цели) при отсутствии переобогащения (Δλ ≥ −0.08) и без роста пропусков (`94E4`).
4. Нет устойчивой зависимости необходимой добавки от оборотов: остаточная ошибка по RPM-ячейкам < 15 % при равных прочих условиях.

**Решение «нужна разработка DKmode»**, если хотя бы одно:

- требуемая добавка устойчиво зависит от оборотов (> 15 % между 2000 и 4000 об/мин при равных Δ / наддуве / ECT) — функция `K_rpm`;
- требуемая величина выходит за пределы, которые даёт `T(Δ)`, или нужны значения вне осей;
- окно 16 мс не даёт различить нужные скорости нажатия, и масштабирование оси не помогает (одинаковый Δ при разных фактических скоростях из DAQ);
- наблюдение расходится с моделью (например, лишние или пропущенные импульсы из-за слияния v73 §2.2) так, что калибровка не устраняет проблему.

В любом из этих случаев следующий шаг — только спецификация модуля и отдельное решение владельца о бинарной разработке. Сборки BIN в рамках v74 нет.

## 8. Исправления документации

- v73 §1.1: интерпретация PKCRH/PKCRL исправлена на **один бит `PKnMD` на вывод** (позиция 2n, нечётные биты зарезервированы, раскладка npkern/Renesas iodefine). Набор выводов не изменился. Добавлен PKIR (`0xFFFFF776`) = `0xC000` (`0x4DD8`, `0x4F5A`): инвертируются PK15 и PK14, **PK0–PK3 не инвертированы**.
- Сверить с официальным Hardware Manual не удалось: доступные PDF не читаются инструментами этой среды (бинарное содержимое). Смысл `PKnMD = 1` → TO8n и функция PKIR остаются **datasheet-dependent**. Достаточно страниц разделов «Pin Function Controller / Port K» и «ATU-II TCR8/TCNR» — их можно приложить для v75.

## 9. Открытые вопросы для v75

1. SHA-256 ROM на автомобиле; повтор модели и адресов на нём.
2. Hardware Manual: PFC Port K, PKIR, ATU-II CKSEL/PSCR/TCNR, CMT CKS.
3. Фактический тик по `94F0` и потери `94E4` на автомобиле.
4. CarBerry BIN: единицы `0x293FA`, выход импульса, RPM-фактор по коду.
5. Поддержка SSM поверх CAN на этом ECU (частота опроса).
